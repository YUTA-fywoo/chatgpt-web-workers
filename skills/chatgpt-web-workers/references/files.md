# File transfer and artifact retrieval

Distinguish **actual file bytes**, a **local path**, **text extracted from a file**, and a **file/content reference**. They are not interchangeable. Use only the files needed by the assigned worker and within the user's authorization for this ChatGPT destination. Honor current upload and sensitive-data permission rules; do not request approval again when the specific transfer is already authorized.

## Fixed routes

- **Upload an original file to Sol:** go directly to the in-app browser upload flow.
- **Receive a file newly generated by Sol:** go directly to the in-app browser download flow. Do not make a preliminary direct-read attempt to obtain its bytes.
- **Send text, source code, or follow-up instructions:** use the Chat webpage composer. Read replies with the internal `read_thread` tool; checking whether a file is ready is not a file-download probe.

Do not invent `attachments`/`files`/`file_path` arguments or add Base64/chunking workarounds. Retest boundaries are in the skill entrypoint; historical evidence is in [validation.md](validation.md).

A Markdown link to a local file remains text; the worker cannot open that host path. Submit staged attachments and their prompt together through the webpage; internal sending is not a file-transfer route.

For a small text/code file when exact file transfer is not required, paste the relevant content with a filename and clear boundaries into the webpage composer. Identify it as supplied text, not an uploaded original. Do not encode entire binary files or large documents into prompts to simulate upload. If formatting, formulas, images, complete content, or an original file matters, upload the file.

## Upload through the in-app browser

1. Use the task's existing Chat and ensure no other prompt is being generated or awaiting dispatch. If the tab was restored or changed externally, synchronize only when necessary and before staging files.
2. Read the browser's current `file-uploads` documentation once for the session. Use the supported file chooser API, grounded in the observed upload control. The tested UI path was **添加文件等 → 添加照片和文件**.
3. Start the documented `waitForEvent("filechooser")` before activating the visible upload control, then call the chooser's `setFiles` with absolute paths. Check `isMultiple()` before a multi-file selection. Do not use undocumented `setInputFiles` or a guessed native-dialog workaround.
4. Wait for actual filename chips and upload readiness. Confirm the selected filenames and count; resolve errors before sending. Submit the prompt and these attachments **together through the browser** and verify dispatch as described in transport.md.
5. Ask for a task-relevant content check, such as sheet names/row counts, a document section, source identifier, or an image observation. A filename chip alone does not prove the worker read the intended content. Do not demand a hash from a worker that lacks a tool to calculate it.

For multiple workers, attach a file only to workers that need it. Chats do not automatically share attachments or local tools. Reuse an already attached file within the same task/chat when it is still accessible. If a file changes, identify the revision and upload the new bytes; do not let the worker analyze the stale version.

Use the original file when fidelity matters. For large files or unsupported formats, prepare a task-relevant supported excerpt/representation with the relevant document/data skill and disclose the conversion and any lost structure. Do not claim universal file-type support merely because the chooser accepts a path.

## Previously uploaded input files

Normal `read_thread` replies may include previously uploaded input attachments. Reuse an already returned local copy when needed; do not make extra reads to probe generated-file reception.

When a read returns an input attachment as `{name, path}`, verify it exists, inspect expected type/content, and copy needed files to the workspace before temporary previews expire. If the original is local and byte identity matters, compare hashes. Track the supplying message so input attachments are not mistaken for worker outputs.

Reads may return or download the same earlier attachments again. Cache verified attachment identities and workspace copies; do not hash, parse, or forward unchanged files repeatedly. Re-verify when the file revision changes or there is evidence of corruption.

Content-reference markers and citation tokens are not downloadable files or usable host-deliverable links; retrieving an input attachment does not establish generated-output retrieval.

## Download newly generated output through the browser

Once the worker reports that its file is ready, inspect that Chat's generated-file card or download control in the in-app browser. Use the supported download event/API. A card may offer a direct download, or first open a Library preview with a separate Download button; follow the current visible flow. An intermediate preview is not a completed download.

Verify the actual downloaded local file before claiming success. Use a path reported by the browser/tool when available. If the supported download event provides no path, inspect the configured download location narrowly using the observed filename and creation time; do not crawl unrelated folders or pick an old same-name file. The tested Windows browser saved to the user's Downloads folder. Handle filename suffixes by matching the new download, not by assuming an exact unchanged basename.

Copy the validated artifact into the task workspace. Keep input, intermediate, and final artifact roles distinct. Put user-facing deliverables in the environment's designated outputs directory; preserve originals. For result files, inspect meaningful content, calculations, encoding, and format or use the relevant document/spreadsheet/code skill. Do not treat download success alone as quality validation.

If the worker returns complete plain text/code and no real downloadable file, the host may create the requested file locally when this preserves the required format. Describe it as locally saved worker content, not a file downloaded from ChatGPT. For rich or binary artifacts, use an actual supported generation/download path or state the concrete limitation.

For an expired attachment/output, request regeneration or re-upload within the same chat and six-chat budget. Do not fabricate a `sandbox:` URL, assume remote and host paths are shared, or route private files through an unrelated public hosting service.
